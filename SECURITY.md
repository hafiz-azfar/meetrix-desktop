# Security model

- Meetrix exchanges InsForge OAuth codes on the server. The OAuth return requires a one-time browser state and PKCE verifier. The app scopes user identities to the configured InsForge project.
- The browser and desktop receive independent, revocable Meetrix cookies for up to 12 hours. Session credentials are hashed at rest. Cookies are HttpOnly and SameSite=Strict, with Secure enabled for HTTPS. Changing the identity provider leaves historical ownership records under their original account identifiers.
- Desktop sign-in uses the system browser. An authenticated browser session must approve a short-lived pairing code, and only the requesting app can redeem the request. The app opens a browser URL built from the active workspace origin.
- Electron content runs in a sandbox with context isolation and guarded navigation. The settings window exposes a limited connection interface. The local server binds to loopback.
- The Windows display picker requires a user gesture in the workspace's top-level frame and explicit source selection. System audio requires a separate opt-in and a full-display source. Meetrix requests Chromium's exclusion of its own playback where supported.
- Host transfer is a serialized meeting operation authorized by the current host. The new host must have an authenticated account and a matching active session in the main room. The transfer records an audit event, replaces the in-room host, and preserves the original organizer. Clients use versioned server role updates and keep the same room-scoped media grants.
- The server requires the active host to grant or revoke co-host roles and end meetings. Co-host actions require a signed-in, admitted user and an active LiveKit participant session matching the host’s grant. Grants are scoped to one meeting and one participant SID. A new connection requires a fresh grant. Co-hosts can moderate attendees and manage breakouts in standard meetings. LiveKit media tokens remain room-scoped and lack administrative grants. Passcodes use salted scrypt, and the API rate-limits requests and issues 50-second initial room grants.
- Accountless attendance requires explicit host opt-in and waiting room admission. A tab keeps a random proof scoped to the meeting. The guest endpoint gives admitted invitees a LiveKit room grant. Workspace APIs, including stored notes, polls, and whiteboards, still require an account.
- Moving an attendee to the waiting room removes their active LiveKit participant, ends their breakout assignment, and blocks new media grants and stored collaboration until readmission. LiveKit Cloud accepts an explicit cutoff for prior grants. Self-hosted LiveKit can still accept a cached, unexpired grant.
- Breakout assignments require host or co-host authorization. The server issues a routing key after admission and stores a hash. It can fetch only the assigned LiveKit grant for that meeting and identity. Guests who are removed cannot request replacement grants. LiveKit carries room chat and media separately per breakout. Automatic moves mute the microphone and turn off the camera, and closing a room retires its ID. Failed room cleanup is retried by the server.
- Standard-room captions and recording notices are accepted from the authenticated LiveKit host identity. Recording consent replies go directly to the host and apply only to one request and one participant connection. Meetrix captures only the host and consenting participants; it stops its recorder when consent is withdrawn, membership changes, or the host connection is interrupted. This controls the built-in recorder. Anyone with access to media can still use separate capture software, and withdrawing consent leaves already captured media on the host device. Encrypted rooms and breakouts omit built-in recording and manual captions.
- A delegated captioner sends text to the host, who validates the current LiveKit session and republishes the caption. Annotation drawing requests go to the presenter. Viewers accept drawing and permission updates from the LiveKit participant publishing the active share. Annotation data is bounded, applies to a single presentation, and is kept in client memory.
- Camera backgrounds use a same-origin bundled MediaPipe model and WebAssembly runtime. The renderer resizes imported images and stores them in the device’s app profile. During an effect, LiveKit receives the composited canvas track. If initialization fails while turning on the camera, Meetrix keeps the camera off. If frame processing fails during an effect, the canvas fills with a solid color. Person detection can make mistakes, especially in poor lighting.
- Notes, poll ballots, and whiteboards are stored in SQLite for standard rooms. Protect the storage volume and backups. Use one backend process for a workspace to keep moderation queues and limits coherent.
- Encrypted rooms use LiveKit media and data encryption. The host distributes the random key separately. Signaling and meeting metadata are still visible to the deployment. Modified clients can publish unencrypted tracks.
- Self-managed LiveKit can accept a previously issued unexpired token after removal. LiveKit Cloud offers provider-side revocation. Hosted deployments require HTTPS and WSS.
- Application signing, production load verification, and independent security assessment remain release work.

Use GitHub's private vulnerability reporting option when available. Keep credentials and private meeting information out of public issues.
